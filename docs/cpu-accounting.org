#+TITLE: %cpu from measured run time (kernels 209 and 212)
#+DATE: 2026-10-30

* Problem
ps, top and btop read l_pctcpu (summed into kinfo p_pctcpu).  Stock
sched_pstats grew it from l_cpticks, the statclock samples (100 Hz) that
found the LWP on a CPU.  Threads woken in phase with the tick (media threads
on the 10 ms audio interrupt) are always or never caught: top showed 28 % for
a Firefox process that ran 4.9 %, ps 0 % for another.

* Kernel 209 (aed62a6)
sched_pstats takes the run time the kernel measures at every switch
(l_rtime, plus the current slice of an LWP on a CPU) and divides the delta
since the previous call (kept in the new l_ps_rtime) by the real elapsed
time.  The exponential decay (ccpu = exp(-1/20)) is unchanged.

* Kernel 212 (42ce62b)
Kernel 209 kept the stock "if (l->l_slptime != 0) continue" after the decay.
With tick samples that skip cost nothing; with measured run time it threw
away the last second of every LWP that happened to be asleep at the 1 Hz
call, which for a bursty thread is most calls.  Removed: a thread that slept
the whole second measures 0 and adds 0.

* Measurement
/var/tmp/duty ON_MS OFF_MS SECONDS (busy loop, then usleep), three at once
for 90 s, ps -o pcpu against TIME/90 s:

| load       | real | kernel 211 | kernel 212 |
|------------+------+------------+------------|
| 50/50 ms   | 45 % | 22.2 %     | 43.4 %     |
| 5/15 ms    | 17 % | 1.0 %      | 15.3 %     |
| 1/3 ms     | 5 %  | 0.0 %      | 4.0 %      |

The remaining shortfall is the 20 s decay average still converging after a
90 s run.
