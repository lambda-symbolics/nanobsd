#+TITLE: imt(4) — I2C precision touchpad for NetBSD (LISPBSD)
#+DATE: 2026-09-20

* Why this exists

NetBSD 11 declares an =imt= device in =dev/i2c/files.i2c= but ships neither
=dev/i2c/imt.c= nor the =dev/hid/hidmt.c= layer that declaration names, so the
device can never be configured and the Elan I2C touchpad attaches only as
=ims(4)= — a two-button mouse with no scrolling.

OpenBSD's =hidmt= cannot be ported across directly: it is written against
OpenBSD's wsmouse multitouch framework (=wsmouse_mtstate=,
=wsmouse_id_to_slot=, =wsmouse_configure=, =wsmouse_input_sync=,
=wsmouse_set_mode=), none of which exists in NetBSD's wscons.  Acquiring that
framework means replacing the shared mouse layer used by every pointing
device — far larger and riskier than the driver itself.

So =imt.c= here is NetBSD-native: it decodes the Windows Precision Touchpad
reports itself and drives the existing wsmouse interface.

* What works

- Attaches on the right report: =imt0 at ihidev0 reportid 4: 3 contacts,
  clickpad, two-finger scrolling=.  It parses the per-contact tip/id/x/y
  locations, the contact-count field and the button, and finds the Input Mode
  feature report (rid 3, 2 bytes including the report id).
- =machdep.imt.{ptp,motion_div,scroll_div,scroll_invert,debug}= tunables.
- Scrolling is emitted as z/w wheel deltas via =wsmouse_input()=, NOT
  =wsmouse_precision_scroll()=: this X configuration consumes the wheel axes
  ("ZAxisMapping 4 5 6 7"), which is also how =pms(4)= delivers the
  TrackPoint's working middle-button scroll.  =wsmouse_precision_scroll()=
  emits =WSCONS_EVENT_[HV]SCROLL=, which that path ignores entirely.
- Position is tracked as the CENTROID of the contacts that are down.  The
  order contacts appear in a report is not stable, so "the first contact
  down" alternates between fingers and the position jumps by the finger
  spacing every report.

* The open problem

Writing Input Mode = 3 (Precision Touchpad) to feature report 3 is accepted
(=err 0=, tried with both a 1-byte and a 2-byte payload; =ihidev_set_report=
prepends the report id itself, so 1 byte is the correct payload length).

After that write the pad stops sending the mouse report — so the pointer dies
— and sends NOTHING in its place.  Instrumenting =ihidev_work()= showed no
input reports of any id arriving at all, and the pad's interrupt does not
appear to fire.  So the mode change is taken, but the device then goes silent
rather than producing multitouch reports.

Unverified hypotheses, in rough order of suspicion:

1. The PTP initialisation is incomplete.  Windows also writes the Latency
   Mode feature report and reads the Certification/Capabilities feature
   report; the pad may refuse to stream until that handshake is done.
2. The report is arriving but is being discarded before it can be logged.
   The first probe was placed after =ihidev_work()='s packet-length
   validation, so an oversized/short packet would =goto out= and look exactly
   like "no reports".  The probe has since been moved to immediately after
   the I2C read to settle this — result not yet observed.
3. =sc_isize= (=wMaxInputLength=) may be too small for the multitouch report,
   so the read itself truncates or fails.

=machdep.imt.ptp= gates the mode switch so the pad can be left working as a
plain mouse while this is investigated.

* Files
- =kernel/dev/i2c/imt.c= (new), =kernel/dev/i2c/files.i2c= (drop the
  nonexistent =hidmt= dependency), =kernel/arch/amd64/conf/GENERIC=
- =kernel/dev/i2c/ihidev.c= carries a temporary report-id/raw-read probe

* Findings after the descriptor-driven handshake (kernel #115)

Three of the earlier hypotheses are now settled by measurement rather than
argument.

** The pad really does enter Precision Touchpad mode

=imt_set_mode()= now reads the Input Mode feature back after writing it.  It
reads 3 after the write and 0 after a write of 0, so the mode switch takes
effect.  The earlier worry that a short write was being accepted and silently
ignored is refuted: =err 0= was not the only evidence, the readback agrees.

** The input buffer is large enough

=ihidev= reports =isize=14= and the report-4 payload is 11 bytes, which with
the report ID and the two-byte length prefix is exactly 14.  Hypothesis 3 in
the list above is refuted.

** GET_REPORT on an input report is not supported by this pad

A polling path (=machdep.imt.poll_ms=) that fetches the input report over I2C
on a timer fails on every attempt, in both mouse and Precision Touchpad mode,
while feature reports read back fine.  Polling therefore cannot be used as a
substitute for the interrupt, and cannot be used to distinguish "no reports"
from "no interrupts" either.

** The full Windows handshake now runs and succeeds

Enumerating the feature reports gave, for this ELAN0670:

| report | usage      | meaning                    |
|--------+------------+----------------------------|
|      2 | 0x000d0055 | Contact Count Maximum (5)  |
|      3 | 0x000d0052 | Input Mode                 |
|      5 | 0x000d0057 | Surface Switch             |
|      5 | 0x000d0058 | Button Switch              |
|      6 | 0xff0000c5 | Win8 certification blob    |
|      7 | 0x000d0060 | Latency Mode               |

The blob at report 6 reads back =fc 28 fe 84 ...=, the standard Microsoft
certification signature, which confirms both the report choice and that
=GET_REPORT= works for large feature reports.

Picking that report needs Linux's rule: the certification report is the one
whose *first* field carries usage 0xff0000c5.  Taking the first match in
descriptor order instead selects report 14, a four-byte report that returns
different bytes on each read.

The bring-up now performs, in order: read the certification blob, read Contact
Max, enable Surface and Button Switch, set Input Mode, set Latency Mode to
normal.  Every step returns success.  Whether the pad now actually reports is
still open and needs a finger on the pad.

** Corrected in =ihidev=

A report ID >= 15 escapes into a third command byte, but the *response* still
carries a one-byte report ID.  =ihidev_get_report()= conflated the two, so it
parsed the response ID as a 16-bit value, rejected every extended-ID report
and would have skipped a payload byte.  Fixed by tracking the command
extension and the response prefix separately.

* The interrupt line is not the problem (kernel #116)

=machdep.imt.kick= powers the device on, resets it and re-runs the handshake.
A reset makes the pad raise its interrupt to acknowledge, so it doubles as a
live test of the interrupt path:

: ihidev: kick: refcnt 2 isize 14 suspended 0 nrepid 15
: ihidev: poweron -> 0
: ihidev: reset -> 0
: ioapic0 pin 118    1*   ...   ihidev0     (was 0)

Three things follow.

- The interrupt is established, unmasked and delivering *now*, not only at
  boot.  Every "the IRQ was never wired up" theory is dead.
- =refcnt 2= means both =ims0= and =imt0= hold the device open, so
  =ihidev_close()='s SET_POWER OFF has not run.  The pad is powered.
- With a finger on the pad the count does not move at all.

The pad therefore answers every command we send it, acknowledges resets on the
interrupt line, and reports nothing whatsoever when touched.  The remaining
question is no longer about the driver's plumbing but about why the sensor
stays quiet, and the next discriminator is whether it is quiet in mouse mode
too, which the =machdep.imt.ptp= toggle can answer without a rebuild.

Note for the earlier note in this file: =vmstat -i= omits zero-count rows, so
"no line for irq 118" there meant only that it had not fired.  =intrctl list=
shows established interrupts regardless of count and is the right tool.

* Root cause: the reporting switches were written into padding (kernel #119)

The discriminating test was to put the pad back in mouse mode and touch it.
It worked: the interrupt count went from 1 to 573 and the pointer moved.  The
pad is healthy, and Precision Touchpad mode specifically is what silenced it.

The cause was in this driver's own descriptor scan, and it is visible in the
log it printed:

: imt: feature rid 5 usage 0x000d0057 pos 0 size 1   <- real Surface Switch
: imt: feature rid 5 usage 0x000d0058 pos 1 size 1   <- real Button Switch
: imt: feature rid 5 usage 0x000d0057 pos 2 size 1   <- padding, stale label
: imt: feature rid 5 usage 0x000d0058 pos 3 size 1   <- padding, stale label

NetBSD's parser clears its usage count after a Main item but keeps the usage
array, so constant padding that declares no usage of its own is returned
carrying the *previous* field's usage.  =imt_scan_features()= kept the last
match, so it saved bit 2 and bit 3 and wrote 0x0c.  Both real enable bits
stayed clear.  Microsoft specifies that these switches control which touchpad
inputs generate interrupts, which is exactly the observed symptom: fine in
mouse mode, completely silent in Precision Touchpad mode.

The fix is to skip =HIO_CONST= items in both =imt_scan_features()= and
=imt_parse_input()=, and to keep the first match rather than the last.  The
scan now selects only pos 0 and pos 1, and the driver writes 0x03.
=tests/imt-padding-reproducer.c= captures the mechanism.

** The configuration reports are write-only on this pad

GET_REPORT fails for report 5, in every mode.  The old code read it, silently
substituted zeroes on failure and wrote anyway, then logged "surface switch =
1 -> err 0" - which was the value requested, not the value achieved.

Both switches are now set in a single read-modify-write, so a failed read
cannot clear the switch written by a previous call.  Falling back to zeroes is
allowed only when the one write covers every writable field of the report,
which is true for report 5 and is why the two switches must be written
together.  Latency Mode is skipped instead of forced, because report 7 also
carries Button Type, which is not ours to overwrite.  The log now distinguishes
a verified value from an unverifiable write.

** Reset is now a transaction

=ihidev_reset()= marks the reset pending before issuing it, and the input
worker recognises the zero-length packet as the acknowledgement and wakes the
waiter.  Feature requests issued while a reset is outstanding can swallow that
acknowledgement.  The wait is bounded at 500 ms and is skipped for the reset
during attach, which runs before the handler and workqueue exist.

* Hybrid frame assembly (kernel #120)

With the switches written correctly the pad reports in Precision Touchpad mode
and the pointer moves, but two-finger scrolling still did nothing.  The reason
is in the report layout rather than in sensitivity.

Report 4 is 11 bytes, which holds exactly one contact record plus scan time,
contact count and the button.  The attach line says as much:

: imt0 at ihidev0 reportid 4: 1 contacts, clickpad, two-finger scrolling

This is hybrid reporting.  A two-finger frame arrives as two packets: the
first carries Contact Count = 2 and one contact, the second carries Contact
Count = 0 - meaning "continuation" - and the other contact.  The old decoder
treated every packet as a complete frame, so a two-finger gesture looked like
two separate one-finger frames, =down= was never 2, and the scroll branch was
unreachable.  No value of =machdep.imt.scroll_div= could have helped.

=imt_intr()= now assembles: a nonzero count opens a frame and sets how many
records to expect, zero appends to the open one, and only a complete frame is
handed to =imt_emit()=.  Contact Count covers the frame regardless of tip
state, so records with the tip up are collected as part of the frame and
simply do not count as fingers.

* Corrections to the reset work

=ihidev_resume()= holds =sc_lock= and called =ihidev_reset()=, which acquired
it again; =poll=true= skips the acknowledgement wait but not the mutex.  That
is a resume panic, introduced by the reset change and not present before it.
Split into =ihidev_reset_locked()=, which requires the lock and is what resume
calls, and a wrapper that takes it.

The acknowledgement timeout also returned success, which defeated the point of
waiting: configuration could still proceed after an unacknowledged reset.  It
now returns an error, and =imt_enable()= propagates a failed handshake instead
of discarding it.

** Known limitation

=imt_set_fields()='s "zero-fill is safe when the write covers the whole
report" rule is asserted by the caller, not checked against the descriptor.
It is correct for report 5 on this pad, whose only nonconstant fields are the
two switches, but it should be validated against the nonconstant field list
before the driver is used on other hardware.

* Working, and what it took

Kernel #120 onward: one-finger motion and two-finger scrolling both work.

The failure had two independent causes stacked on top of each other, and each
one alone was enough to produce silence or no scrolling:

1. The reporting switches were written into padding, because the descriptor
   scan trusted usages that NetBSD's parser had carried over onto constant
   items.  This kept the pad silent in Precision Touchpad mode while mouse
   mode still worked.
2. The decoder treated each packet as a complete frame, but the pad reports
   in hybrid mode with one contact per packet, so a two-finger gesture never
   looked like two fingers.

Both were found by the same method: put the pad in a mode known to work,
compare, and read the driver's own log rather than reasoning about what the
hardware "should" do.  The mouse-mode interrupt count going from 1 to 573
under a finger is what turned this from guesswork into a bisection.

** Diagnostics removed after the fact

The =ihidev_repdebug= raw/dispatch probes and the =machdep.imt.poll_ms=
polling thread are gone.  The polling path is worth remembering as a dead end:
this pad fails =GET_REPORT= on input reports in every mode, so polling could
never substitute for the interrupt, and a failed poll said nothing about
whether reports were available.  =ihidev_get_report()='s failure message is
now =aprint_debug_dev=, since a refused read is a normal answer on this
hardware and the caller decides whether it matters.

=machdep.imt.kick= is kept deliberately: it powers the device on, resets it
and re-runs the handshake, which is the fastest way to tell a wedged pad from
a driver bug without rebooting.
