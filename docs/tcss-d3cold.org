#+TITLE: TCSS D3cold: the USB-C xHCI power resource and PC10
#+DATE: 2026-10-14

* What the firmware says (full disassembly 2026-10-14)

All 14 ACPI tables disassembled standalone with iasl (the SSDTs redefine
each other's names, so =-e= cross references fail; the per-table output is
good enough to read method bodies).  Workstation copies:
=/root/astra/acpi-dsl/*.dsl= and the concatenation =/root/astra/pc3-acpi.asl=.
The TCSS table is SSDT9 (OEM id =TcssSsdt=).

- =\_SB.PC00.TXHC= (_ADR 0x000D0000, the USB-C xHCI, pci 0:13:0) has
  =_PR0 == _PR3 == { \_SB.PC00.D3C }= under =If (TRTD)=.  =_PS3= only sets
  PME_EN in PMCSR, =_PS0= clears it.
- =D3C._OFF= -> =TCOF=: refuses if any of =TXHC/TDM0/TDM1.SD3C= is set,
  otherwise sends the TCSS device-disable through the pCode mailbox
  (=DSCR=) and loops until =TXHC.VDID= reads 0xFFFFFFFF, then sets IOM
  =TD3C = 1=.  That is TCSS D3cold: the function disappears from PCI.
- =D3C._ON= -> =TCON=: clears =TD3C=, waits up to 100 ms for =TACK=, then
  loops until =TXHC.VDID= reads back (re-enable through =DSCR=), runs the
  TBT DMA re-init (=TXDC.SINT=) when =TDCE && IMRY=.  A timeout is only
  logged, the method still returns.
- =D3C._STA= returns a cached software flag, not =TD3C/TACK=.
- The Thunderbolt DMA engines =TDM0/TDM1= (0:13:2, 0:13:3) reference the
  same =D3C= (plus =TBT0/TBT1=) from both =_PR0= and =_PR3=.

* Why kernel 157's restore killed xhci0

Stock =acpi_power.c= keeps one reference list per resource.  Moving TXHC
D3 -> D0 references the =_PR0= set (=D3C._ON=: TCON, the controller comes
back) and then releases the =_PR3= set (=D3C._OFF=: TCOF, the controller
goes away again).  The next xhci resume saw dead registers
("resume timeout, USBSTS.RSS"), =acpi_power_get= then read D3.  Astra
(follow-ups 8 and 9) predicted exactly this from the AML.

The same bug is what made =idle_d3= and the s2idle table work so far: the
"D3hot" requests for TDM0/TDM1, IPU, ISH, HECI and GNA released their
resources through the broken bookkeeping, which is what the LPS0
requirements (=LPSS_PG=, =IS_D3=) and the PC10 residency need.  A correct
backend keeps every resource that is in both =_PR0= and =_PR3= on, so it
must grow an explicit D3cold or we lose SLP_S0 and PC10.

* The design

1. =acpi_power.c= (Astra, brief in =/root/astra/brief-acpi-power.org=):
   reference the target set before releasing the old one, shared
   resources go _OFF only with their last consumer, failures propagate,
   new =ACPI_STATE_D3_COLD= = _PS3 + release of every reference, D0 from
   D3cold = reference _PR0 (_ON) then _PS0, host test harness.
2. =acpi.c= (commit 38fb502): the =idle_d3= and =s2idle= ADR tables carry
   per-entry flags.  =ADRPWR_COLD= entries (TDM0, TDM1, TXHC, IPU, ISH,
   HECI, GNA) get PCI configuration space captured and PMCSR D3hot before
   =acpi_power_set(D3_COLD)=, and after the D0 restore the function is
   checked for presence (vendor id) and its configuration restored
   (=pci_conf_restore=) and PMCSR set to D0.  =ADRPWR_NODRIVER= (TXHC) is
   skipped while a driver is attached to the function.  The PCH xHCI
   (Bluetooth, camera, fingerprint behind it) and the dwiic controllers
   stay D3hot.
3. =usb= script (commit cb62861): with =USB_TCSS_D3=1=, =usb off= detaches
   xhci0 (=drvctl -d=; nothing internal is on the USB-C controller),
   suspends xhci1 and sets =idle_d3=1=; =usb on= clears =idle_d3= (the
   resource comes back, config restored), rescans pci0 so xhci0 attaches
   fresh (xhci_init, no warm resume of a reset controller), resumes xhci1.

* Detach panic (kernel 157, 22:15)

=drvctl -d xhci0; drvctl -r pci0= on kernel 157 panicked in
=callout_next_ticks= from the idle loop (NULL list link, cr2 0x2d): the
runtime PM idle scan callout from kernel 156 (=sc_rt_callout=) was never
halted or destroyed in =xhci_detach=, so the freed softc stayed on the
callout wheel.  Fixed in commit b72419f (=sc_dying=, =callout_halt=,
=callout_destroy= before the rings are freed).  Dump: =/var/crash/netbsd.18=.

* Kernel 159/160 findings (23:00-23:15)

- Kernel 159 (Astra's backend b61eb1b + the D3cold tables): all seven
  idle_d3 entries went D3cold and came back D0 cleanly, xhci0 reattached
  by the rescan, but 0:13:0 still answered on PCI and PC10 stayed 0 %:
  the Thunderbolt PCIe root ports TRP0/TRP2 (0:7:0, 0:7:2, ppb drivers,
  nothing behind them) list {D3C, TBT0|TBT1} in _PR0 under TRTD, so the
  correct backend keeps D3C on for them.  Kernel 160 adds both as D3cold
  entries in the idle_d3 and s2idle tables (commit 0c2b722).
- Kernel 160 panicked in the first =usb on= of the test, before any
  cold-off: =xhci_resume= rang a doorbell at a garbage offset.  The
  runtime PM scans (kernel 156) walk slot ids 1..sc_maxslots but the
  slot array had sc_maxslots entries, so index 64 was the neighbour's
  memory; its stale "pending doorbell" mask was nonzero on that boot.
  Commit a866d5c allocates sc_maxslots + 1 entries.  Dump
  =/var/crash/netbsd.19= (deleted after analysis).

* Kernel 161/162: the PC9 ceiling and its cause (00:00-00:20)

With kernel 161 the complete cycle worked (TXHC/TDM/TRP all read 0xffffffff
while cold, restore + pci0 rescan brought xhci0 back) but the package sat in
PC9 at 97 %, where kernel 157's cold state had shown PC10.  Panel-off A/B on
161: TCSS cold 1.35 W (PC9 97 %) versus plain usb off 1.95 W (PC3/PC10
split).  Ruled out on kernel 162 with =hw.acpi.sleep.idle_d3_exp= (bit 1:
root ports cold without _PS3 through Astra's =acpi_power_set_flags(...,
ACPI_POWER_NOPS3)=; bit 2: no PMCSR D3hot before the cold-off): all four
combinations PC9.  Cold-from-boot: PC9.  The -x trace showed every resource
reaching _STA 0 (TBT0 _OFF, TBT1 _OFF, D3C _OFF).

The cause was the USB-C controller's state at the moment the power went:
kernel 157 had it *suspended* by the driver (ports quiesced, controller
state saved, PMCSR D3hot from the PCI bus driver); the new script only
*detached* it, which leaves a halted controller with its PHY/ports live, and
the TCSS then stops at PC9 after the cold-off.  =drvctl -S xhci0= before
=drvctl -d xhci0= gives PC10 at 97-98 % every time, restore works, and
=usb off= now does that by default (commit a2bda6a; =USB_TCSS_D3=0= opts
out).  Oddity: after a reattach xhci0 reports "xHCI version 1.10" instead of
1.20; it works.

s2idle caveat: TXHC is not in the s2idle table (its driver is suspended by
pmf there, and a D3cold'ed controller cannot be warm-resumed), so with USB
*on* at lid close the TCSS stays powered during s2idle and D3C is held;
with the default boot state (usb off = cold) the cold state simply persists
through s2idle (entries already in the target state are skipped and not
restored).  A power-loss-aware xhci_resume (full reinit) would remove the
caveat.

* 2026-10-15: lid suspend broken by the filesystem barrier, kernel 163

User report: lid close stalled Bluetooth audio for under a second and did not
suspend.  /var/log/messages: every attempt ended one second after
"s2idle: freezing" with "filesystem barrier failed (16), aborting freeze".
The barrier (c45c6e0, first deployed on kernel 157) requires every non-system
LWP to be in LSSUSPENDED one second after the freeze kick; LWPs in kernel
waits (kevent/poll/select re-sleep without visiting userret, uninterruptible
sleeps) never get there, so the precondition fails even on an idle machine
(verified on kernel 163: "filesystem barrier not established (16)").
Kernel 163 (e5f674d) makes the barrier best effort:
=hw.acpi.sleep.freeze_fsbarrier= 0 off, 1 (default) try and continue
without it, 2 the old abort.  Freeze test on 163: 20 s hold, PC10 97 %,
resumed.  Astra was asked to redesign the precondition.  Kernel 163 also
defaults the Thunderbolt root ports to cold without _PS3 (f022b96).

* 2026-10-15 afternoon: USB domains, kernel 164

- =usb= now has domains: =usb on|off pch= (xhci1, the internal devices)
  and =usb on|off usbc= (xhci0 + the TCSS cold-off); =all= is the default.
  Status is derived from PMCSR (the PCI bus driver puts a suspended function
  in D3hot), the old "uhub children exist" check was meaningless.  A failed
  =idle_d3=1= now fails the command.  bluetooth/webcam/bt-headphones use
  =usb on pch=, so the USB-C block stays cold while Bluetooth plays;
  =bt-headphones off= brings the radio down and suspends the PCH controller
  again unless the camera is attached (commit 66e4379).
- Evidence for the split: this morning's lid s2idle with USB fully on held
  PC10 at only 50 % (TCSS warm, D3C held by the suspended xhci0) against
  98 % cold.
- Kernel 164 = 163 + Astra's 5081c25 (barrier gated on mount operations
  instead of "every LWP suspended"; the vfs_mount patch also touches
  vfs_syscalls.c now, re-applied on stock).  Freeze test on battery:
  "filesystem barrier over 6 mounts", 20 s hold, PC10 98 %, resumed.
- Astra has the brief for the power-loss-aware xhci_resume

* Bluetooth radio A/B (kernel 164, panel off, battery, 240 s windows)

| state                                    | Wh rate | sensor | pc10   |
| everything off (boot state)              | 1.20 W  | 1.33 W | 97.0 % |
| PCH on, ubt0 up, no stream, TCSS cold    | 2.25 W  | 2.14 W | 0.1 %  |
| PCH on, ubt0 up, no stream, TCSS warm    | 2.55 W  | 2.53 W | 0.0 %  |
| PCH on, ubt0 up, no stream, TCSS cold (2)| 2.40 W  | 2.16 W | 0.1 %  |

The domain split is worth about 0.3 W while Bluetooth is up, but an idle,
silent radio costs about 1 W by itself and removes PC10 entirely: ubt(4)
keeps its interrupt and bulk-in pipes open from "up" onwards, and the
kernel 156 runtime PM only parks devices with no open pipes, so the port
stays in U0 and the PCH controller in D0.  (Controllers on with every port
in U3 measured PC9 97 %, 1.40 W earlier.)  Linux parks btusb with the
pipes conceptually open: the driver's suspend callback kills the URBs and
its resume resubmits them, with remote wakeup.  The equivalent here is a
ubt runtime suspend/resume hook driven by the xhci idle scan (abort the
pipes, port to U3 with remote wake, reopen on wake).  Until then
=bt-headphones off= takes the radio down.

* Bluetooth radio parking, kernels 165-171 (afternoon/evening 2026-10-15)

Astra's xhci draft (52989d6: power-loss-aware resume + parking of a ubt
slot with open pipes) plus my ubt pmf handlers (9454563, Astra's fix
e744b2c).  What it took on the hardware:
- 165: four build fixes (shadowed names, the stock XHCI_HCS2_MAXSPBUF macro
  has no outer parentheses, device_pmf_is_registered is not exported).
- 165: every warm resume of xhci1 refused: Tiger Lake reports HCIVERSION
  1.10 after any PCI D3hot cycle (1.20 at attach).  The version is now
  informational (34c10c3).
- 166: every warm resume taken cold: the operational registers read zero
  after D3hot, which the warm path expects and rewrites before CRS.  Now a
  fatal USBSTS marks the state lost up front, otherwise the CRS timeout of
  the warm path is the trigger for cold recovery (f9b3987).
- 167: cycle works (park, inquiry wake, freeze with a parked radio) but the
  radio never parked after a plain =usb on pch=: =drvctl -R= resumes the
  named device and its *ancestors* only (kern_drvctl DRVRESUMEDEV without
  DEVPM_F_SUBTREE, which drvctl(8) does not expose), so ubt0 kept its drvctl
  pmf suspension from the boot-time =usb off= and the parkable predicate
  (active ubt child) refused it.  Found with =hw.usbpm.debug= (ded9afb,
  8125f62, dv_flags + suspensor names).  Fix: the usb script resumes the
  whole subtree, leaves last (125f41d).
- Result on 171: PCH controller on, radio up and parked, TCSS cold: PC10
  98 %; =btconfig ubt0 inquiry= wakes it (remote wake counted) and works.
