#+TITLE: Hardware video decoding (VA-API) on the Tiger Lake GPU
#+DATE: 2026-10-02

* Result

Firefox playing a 1440p60 VP9 clip under Mahogany, panel on: package power
7.5 W -> 3.0 W, the content process 33 % -> 5 % CPU, max 56 -> 37 C.  Decode
alone (ffmpeg, 1440p60): software 2.5 W at 111 % CPU, iHD 1.6 W at 5 %.
Hardware output is bit-exact with the software decoder (framemd5, 1080p30
and 1440p60).  A busy YouTube tab still uses CPU on its main thread (page
scripts); the decode itself runs in the RDD process at ~0 %.

* Pieces

- Kernel: NetBSD's i915 exposes both VCS engines and VECS, but nothing had
  used them.  Two port bugs panicked on the first media context:
  - kernel 132, =rcu_replace_pointer= assigned a local copy, so
    =set_engines()= freed the live engine map;
  - kernel 133, a NetBSD =rb_tree= needs its ops and Linux never initialises
    the virtual-engine tree (zero is an empty Linux rbtree), so the
    load-balanced VCS submission faulted.
- =userland/vaapi/build.sh=: gmmlib 22.10.0 and intel-media-driver 26.1.5
  with FreeBSD's port patches, two NetBSD fixes, installed in =/usr/local=.
  It also links =iHD_drv_video.so= into =/usr/pkg/lib/dri= (libva's search
  path) and =/usr/local/lib/libdrm.so.2= to NetBSD's =libdrm.so.3=: Firefox
  dlopens the Linux soname, and without it its DMA-BUF device, and with it
  VA-API, silently fails ("Failed to load libdrm.so.2").
- Firefox (=user.js=): =media.hardware-video-decoding.enabled= and
  =force-enabled=, and =media.rdd-process.enabled= with =rdd-ffvpx= and
  =rdd-ffmpeg=: the NetBSD build has the RDD process off by default, and
  VA-API only runs there.

* Checking

=about:support= (Compositing, Codec Support Information), =about:media=
during playback, or =pmap= on Firefox's processes: =iHD_drv_video.so= in the
RDD process means hardware decoding.  =/usr/pkg/lib/firefox/vaapitest -d
/dev/dri/renderD128= is Firefox's own probe.  For logs:
=MOZ_LOG=PlatformDecoderModule:5,FFmpegVideo:5,Dmabuf:5=.

Not yet tested: AV1 content, the X11 session.

* Kernel 143: virtual-engine tree collisions (panics 10-05 and 10-10)

Two "panic: trap" dumps (/var/crash/netbsd.14, 10-05 13:53, and
netbsd.17, 10-10 12:46) have the same chain:
=contexts_free_all -> __free_engines -> virtual_context_destroy
(intel_lrc.c:4737) -> rb_erase_cached -> rb_tree_remove_node=, a write
through a NULL parent in =rb_tree_prune_node= (rb.c:515).  Read with
=gdb -batch -ex 'target kvm netbsd.17.core' -ex bt compile/GENERIC/netbsd.gdb=;
the node (=p *(struct ve_node *)=) had =inserted = true=, =prio 3=,
=order 6= and all links zero, and the sibling's tree was empty.

Cause: the NetBSD port keys the per-engine virtual tree by (prio, order)
with =order= counted per virtual engine ("XXX kludge to get insertion
order").  Two virtual engines (two video decoders, Firefox and mpv or two
Firefox streams) at the same priority produce the same keys; the second
=rb_tree_insert_node= returns the first engine's node, the only check is a
KASSERT (GENERIC has no DIAGNOSTIC), the node is flagged inserted anyway,
and when that context is freed the erase of a node that is not in a tree
faults.  Kernel 143 (cb3832f): the counter is per sibling engine
(=execlists.virtual_order=, under =active.lock=), the compare puts the
highest priority leftmost as Linux does (rb_first = highest), =first= is
=RB_TREE_MIN(tree) == node=, and a collision, now impossible, is logged
and the node left out instead of flagged.

Crash dumps: savecore(8) writes them to =/var/crash= as =netbsd.N.core.gz=
plus the kernel =netbsd.N.gz= (=bounds= holds the next N, =minfree= the KB
of free space below which it refuses), and nothing ever removes them;
5.8 GB were there on 10-10 (netbsd.2 to netbsd.7 from September also
uncompressed).  The panic line and time are in /var/log/messages as
"savecore: reboot after panic".
