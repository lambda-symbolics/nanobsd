#+TITLE: 802.11n on the Nano's AX201 (iwx)
#+DATE: 2026-10-22

* What it is
NetBSD 11's net80211 only knows 11a/b/g, and our iwx(4) port had OpenBSD's
HT code stripped.  Kernels 193-198 put 802.11n station mode back, modeled on
OpenBSD:

- net80211 (=kernel/net80211=): HT Capabilities/Operation parsing in beacons
  and the association response, our HT Capabilities element in the
  (re)association request, HT negotiation (=ieee80211_ht_negotiate=, CCMP or
  open only), Block Ack action frames (ADDBA request/response, DELBA), the
  transmit agreement state with backoff, A-MSDU decapsulation, and a separate
  non-QoS sequence counter (index 16; it used to share TID 0's, which would
  punch holes into a TID 0 Block Ack window).
- iwx: HT rates and firmware rate control (MCS 0-15, SGI, STBC), 40 MHz PHY
  context, HT station flags and protection, the firmware Rx Block Ack session
  and the driver reorder buffer (with a 100 ms gap timer, as Linux), BAR and
  firmware frame-release notifications, Tx aggregation queues and compressed
  Block Ack reclaim.

* The switch
=hw.iwx.ht= (0/1) decides what the *next* association offers; it is 1 in
=/etc/sysctl.conf=.  To go back: =sysctl -w hw.iwx.ht=0; wpa_cli -i iwx0
reassociate=.  HT also turns WME (QoS) on, as an HT station must be a QoS
station.  =hw.iwx.ht_status= shows the association (width, SM power save,
AP MCS), Rx Block Ack sessions, reorder counters, the last Rx/Tx
=rate_n_flags= (0x0010ca17 = HT MCS 15, 40 MHz, SGI) and Tx aggregation.

* Tx aggregation is the firmware's job
The AX201 firmware sends the ADDBA request and consumes the AP's response
itself once the driver binds an aggregation queue to the TID (OpenBSD's
IEEE80211_C_ADDBA_OFFLOAD; =ic_addba_offload= here).  Requests sent by
net80211 were acked by the AP but never answered (kernel 197 probe), and the
answers never reached the driver.  So net80211 just calls
=ic_ampdu_tx_start= when a TID carries QoS data.

* SM power save
With =powersave= on, the association request asks for dynamic SM power save
and the PHY context listens on one chain, the second waking on the AP's RTS
(Linux's default).  Same download rate as with both chains always on.

* Measured (2026-10-22, Zyxel 5 GHz ch 40, 40 MHz below, LAN peer on Wi-Fi)
| direction | legacy 11a | HT, kernel 194 (Rx only) | HT, kernel 198 |
|-----------+------------+--------------------------+----------------|
| download  | 13 Mbit/s  | 39-45 Mbit/s             | 100-112 Mbit/s |
| upload    | 12.6       | 16-17                    | 100            |

* 802.11ac (VHT, 80 MHz): kernel 200, on since 2026-10-22 evening
Behind its own switch, =hw.iwx.vht= (needs =hw.iwx.ht=1, 5 GHz only), 1 in
=/etc/sysctl.conf=.  Written that morning without the Nano and
compile-checked in the gefs VM (/build/agent-vht there), then run:

- Kernel 199 associated as HT only: the Zyxel's basic VHT-MCS set 0xffaa
  asks for MCS 0-9 on *four* streams, which a 2x2 client can never meet.
  Linux ignores the basic set outside strict mode for this reason; OpenBSD
  passes it by accident (NOT_SUPP = 3 compares as "more").  Kernel 200
  checks only the streams we have.
- Kernel 200: =assoc=vht width=80=, rx and tx =rate_n_flags= 0x0010d319 =
  VHT MCS 9, 2 streams, 80 MHz, SGI (866 Mbit/s).  The AP had moved to
  primary channel 48 (center 42: control position 2 above), which worked.

| LAN, 20 s each (Wi-Fi peer on the same channel) | HT40       | VHT80           |
|-------------------------------------------------+------------+-----------------|
| download                                        | 109 Mbit/s | 119, 144, 181   |
| upload                                          | 98         | 123, 128        |

CPU stays 99.5 % idle at 181 Mbit/s (software CCMP).  The limit is the
shared channel: the test peer is a Wi-Fi client of the same AP, so every
byte crosses the air twice.

- net80211: VHT Capabilities/Operation elements parsed from beacons and
  the association response (=ieee80211_setup_vhtcaps/vhtop=, OpenBSD's
  center-frequency logic incl. 802.11-2016 160 MHz signalling, with two
  OpenBSD slips fixed: the 80 MHz center list had 112 for 122, and a
  deprecated 160 MHz BSS was cut to 80 MHz with the center 4 instead of 8
  channel numbers off), =ieee80211_vht_negotiate= (HT first, AP basic
  VHT-MCS set), our VHT Capabilities element after the HT one.
- iwx: VHT capabilities (80 MHz, SGI80, MCS 0-9 on two streams, 3895-byte
  MPDUs, 1 MB A-MPDUs, Rx STBC 1), 80 MHz PHY context with the control
  channel position from the center (=iwx_get_vht_ctrl_pos=), ADD_STA 80 MHz
  + VHT MIMO + A-MPDU length from the VHT caps, TLC in VHT mode,
  =hw.iwx.ht_status= with =assoc=vht=, =width=80=, the AP's VHT elements and
  rx_vht80/rx_vht counters.  No 160 MHz: we do not offer it.
- The Zyxel (seen from the workstation): primary 40, secondary below, VHT
  80 MHz centered on 42 (control position 1 below), basic VHT-MCS 0xffaa =
  MCS 0-9 on two streams required (we offer exactly that), AP max MPDU
  7991, no 160.

** Test procedure (as run)
1. Build on the laptop from nanobsd (net80211/*, dev/pci/if_iwx.c,
   if_iwxvar.h), install as kernel 199, 198 stays the previous entry.
2. Boot; =hw.iwx.ht=1=, =hw.iwx.vht=0= as before: same as 198.
3. =nohup sh userland/iwx-ht/ht-test.sh vht= (dead-man: back to HT if the
   WireGuard peer is silent for 60 s), then =hw.iwx.ht_status= should say
   =assoc=vht ... width=80=, rx rate mod type VHT (=rate_n_flags= bits 8-10
   = 3) at 80 MHz (bits 11-13 = 2).
4. A/B against HT on the LAN: =KNOB=hw.iwx.vht sh ht-ab.sh URL= and
   =KNOB=hw.iwx.vht sh up-ab.sh= (ncat listener on the workstation).
5. If good: =hw.iwx.vht=1= in /etc/sysctl.conf.
